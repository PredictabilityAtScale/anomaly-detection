# Anomalyzer 0.9.0

Adds explicit forward models and horizon-aware automatic method/setting
comparison without changing existing forecasting or anomaly-detector defaults.

- `forecast_with_model` supports naive, seasonal-naive, recent mean/median,
  simple exponential smoothing, UsageTap-compatible local trend, damped local
  trend, and the existing Anomalyzer family. Components, parameters, fit windows,
  completeness and calendar alignment remain inspectable.
- `select_forecast` evaluates a bounded default catalog or caller-supplied
  candidates on identical chronological holdouts at the full requested horizon.
  It exposes MAE, RMSE, WAPE, bias, per-lead errors, failed candidates and the
  chosen settings, then refits that model. Objectives are MAE, RMSE or absolute
  horizon-total error; no hidden one-step veto overrides that choice.
- New `forecast-model-v1` and `forecast-selection-v1` request/result contracts
  keep these forward-only APIs separate from `forecast-v1` historical references
  and native anomaly calibration. Existing calls retain their numerical policy.
- Synthetic parity fixtures were evaluated by unmodified UsageTap Current
  functions. Nested outer evaluation demonstrates the distinction between
  selection error and subsequent forecast error, including unseen changes.
- The README explains trend, seasonality, cycles and residuals: residuals include
  ordinary noise, model error and possible anomalies. Lower forecast error alone
  does not prove better incident detection; adaptation can absorb changes.

The default grid has 15 candidates, three disjoint full-horizon folds, an initial
28-observation prefix and a shared ten-second cooperative budget. Callers can
configure bounded candidate lists, fold count, loss and runtime. A 14-step
selection needs at least 70 complete observations. Insufficient evidence is
explicitly unavailable. Fixed selected models preserve horizon prefixes;
reselection for another horizon may choose differently. Numerical ties keep
candidate order. Neither validation loss nor model parameters imply calibrated
uncertainty, health or future optimality.

UsageTap adoption must explicitly call the new APIs, pin the released wheel and
transitive hashes, validate its transport budget, retain Current comparison and
keep detector references/calibration independent. The compatibility bridge's
engine pin is 0.9.0; that bridge still calls `forecast_series` and does not enable
selection by a version upgrade. See the
[API and limitations](../forecasting.md#explicit-models-and-horizon-aware-selection-090),
[UsageTap handoff](../usagetap-forecast-migration.md#090-model-selection-adoption),
and [immutable release workflow](README.md). Publishing requires supported-Python,
installed wheel/sdist and offline Linux/Python 3.12 Lambda verification.
